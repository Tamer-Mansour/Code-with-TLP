# The OS-Hardware Contract

Modern operating systems do not directly control hardware through any special magic — they rely on a well-defined contract established by the CPU architecture. On RISC-V this contract is called the **Privileged Architecture Specification**, and it defines exactly what the hardware provides and what the software must do in return.

## Why a Contract Exists

Every CPU must answer two fundamental questions: who is allowed to do what, and how does control transfer between code running at different trust levels? Without a contract, any program could reprogram interrupt controllers, overwrite kernel memory, or spin the CPU forever. The contract prevents this by splitting the machine into privilege levels.

## RISC-V Privilege Levels

RISC-V defines three privilege levels (modes):

| Mode | Level | Typical Occupant |
|------|-------|-----------------|
| Machine (M) | Highest | Firmware / OpenSBI |
| Supervisor (S) | Middle | OS kernel (Linux, xv6) |
| User (U) | Lowest | Applications |

Hardware enforces these levels — a U-mode instruction cannot read an S-mode Control and Status Register (CSR). Attempting to do so raises an **illegal instruction** trap.

## CSRs: The Kernel's Control Panel

Control and Status Registers are the primary mechanism through which privileged software configures the processor:

- `mstatus` / `sstatus` — global interrupt enable, previous privilege level
- `mepc` / `sepc` — exception program counter (where to return after a trap)
- `mcause` / `scause` — reason for the last trap
- `mtvec` / `stvec` — base address of the trap handler
- `satp` — supervisor address translation and protection (page table root)
- `mie` / `sie` — interrupt enable bits per source

Reading a CSR in assembly:

```asm
csrr  a0, sepc      # read supervisor exception PC into a0
csrw  stvec, a1     # write trap handler address from a1
csrrs a2, sstatus, t0  # atomic read-set: set bits, keep old value in a2
```

## What the Hardware Guarantees

When a trap (interrupt or exception) occurs the hardware atomically:

1. Saves the current PC into `sepc` (or `mepc` in M-mode).
2. Records the cause in `scause`.
3. Clears interrupt enable in `sstatus.SIE`.
4. Switches privilege to Supervisor mode.
5. Jumps to the address in `stvec`.

The OS kernel must then save the rest of the processor state (registers, stack pointer) in software — the hardware does **not** push registers automatically. This is a common pitfall: forgetting that `a0`–`a7`, `ra`, and caller-saved temporaries are trashed the moment any function is called inside the trap handler unless you save them first.

## What the OS Must Provide

In return for the hardware's guarantees, the OS must:

- Install a valid trap vector in `stvec` before enabling interrupts.
- Configure the Physical Memory Protection (PMP) registers or page tables before dropping into U-mode.
- Never return from a trap handler with a corrupted stack pointer — the hardware will happily resume execution at whatever address `sepc` holds.

## A Worked Example: Enabling Interrupts

```c
// xv6-riscv style: enable supervisor timer interrupt
void intr_on(void) {
    // set SIE bit in sstatus, enable supervisor interrupts
    w_sstatus(r_sstatus() | SSTATUS_SIE);
}
```

The corresponding assembly generated by the compiler calls `csrrs` with the SIE mask. If the OS calls this before setting `stvec`, the first interrupt will jump to address 0 and crash — a classic kernel boot bug.

## Common Pitfalls

- Enabling interrupts before the trap vector is installed.
- Forgetting that `scause` bit 63 distinguishes interrupts (1) from exceptions (0).
- Confusing M-mode and S-mode CSR names (e.g., `mtvec` vs `stvec`).

> **Interview answer:** The OS-hardware contract on RISC-V is the Privileged Architecture spec: the hardware enforces privilege levels, atomically saves minimal state (PC, cause, privilege) on a trap, then hands control to the kernel's registered `stvec` handler — the kernel saves the rest.
