# Synchronous vs Asynchronous Events

Understanding whether an event is **synchronous** or **asynchronous** is fundamental to reasoning about interrupt handling, debugging, and real-time system design. The distinction controls when an event can fire, how repeatable it is, and how an OS must respond.

---

## Core Definitions

| Property | Synchronous | Asynchronous |
|----------|-------------|--------------|
| Caused by | The currently executing instruction | An external source (hardware, another CPU) |
| Timing | Predictable — same input always triggers at the same point | Unpredictable — can arrive between any two instructions |
| Reproducible? | Yes | Not guaranteed |
| Examples | Divide-by-zero, page fault, `syscall` | Timer tick, disk I/O complete, NIC receive |

---

## Synchronous Events

A synchronous event is **caused directly by the instruction the CPU is currently executing**. If you run the same program with the same data, the event fires at exactly the same instruction every time.

Classic synchronous events:

- **Divide-by-zero** (`#DE`, vector 0) — triggered by a `div` instruction with a zero divisor.
- **Page fault** (`#PF`, vector 14) — triggered when a memory access hits an unmapped or protected page.
- **Invalid opcode** (`#UD`, vector 6) — triggered by an unrecognized instruction encoding.
- **System call** — triggered by `syscall` / `int 0x80` in user code.

```c
// This always triggers a synchronous SIGFPE at this exact line:
int a = 10, b = 0;
int result = a / b;  // #DE exception — synchronous
```

Because synchronous events are reproducible, the OS can handle them deterministically: catch the fault, fix the root cause (e.g., map a page), and retry the faulting instruction.

---

## Asynchronous Events

An asynchronous event is **generated by a source outside the currently running instruction stream**. The CPU learns about it only at an instruction boundary (after completing the current instruction).

Classic asynchronous events:

- **Hardware timer interrupt** — fires every N milliseconds regardless of what user code is doing.
- **Keyboard or mouse input** — raised by the I/O controller when the user acts.
- **Network packet arrival** — NIC raises an IRQ when data lands in its buffer.
- **Inter-processor interrupt (IPI)** — one CPU core signals another.

```
Time ──────────────────────────────────►
CPU:  [instr A] [instr B] [instr C] [instr D] ...
                      ▲
                      │ NIC raises IRQ (async)
                      └── CPU sees it AFTER instr B completes
```

Because the timing is unpredictable, asynchronous events must be handled in a way that is **safe regardless of which instruction was interrupted**. This is why ISRs must save and restore the complete CPU state.

---

## Why the Distinction Matters for the OS

### Fault recovery

Synchronous events allow **fault-based recovery**. A page fault handler can:
1. Allocate and map the missing page.
2. Return to the *exact same instruction* that faulted.
3. The instruction re-executes — this time it succeeds.

Asynchronous events do not "belong" to any instruction, so there is nothing to retry.

### Reentrancy and locking

Because asynchronous interrupts can arrive at any time, any data structures shared between normal code and ISRs must be protected (e.g., by disabling interrupts with `cli` on x86, or using spinlocks in SMP kernels).

### Real-time constraints

Hard real-time systems must bound interrupt **latency** — the maximum time from when an async event fires to when the ISR begins executing. Synchronous events by definition have zero latency: they block the instruction from completing.

---

## Worked Example

A process calls `malloc()`, which touches a new virtual address:

1. The `mov` instruction accessing the new page triggers a **synchronous** page fault.
2. The page fault handler maps physical memory.
3. While the handler runs, a **timer IRQ** fires — this is **asynchronous**.
4. The kernel's interrupt-disabled critical section defers the timer until the fault handler exits.
5. The `mov` instruction is re-executed and succeeds.

> **Interview answer:** A synchronous event is caused by the current instruction and is reproducible; an asynchronous event is caused by external hardware and can arrive between any two instructions. Synchronous events enable fault-and-retry recovery; asynchronous events require ISRs to save full CPU state because they interrupt arbitrary code.
