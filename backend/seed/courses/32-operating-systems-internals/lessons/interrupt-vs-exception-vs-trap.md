# Interrupt vs Exception vs Trap

Modern CPUs handle unexpected or special events by temporarily suspending normal execution and jumping to a dedicated handler. Three closely related mechanisms accomplish this: **interrupts**, **exceptions**, and **traps**. Confusing them is one of the most common gaps in systems interviews — this lesson draws sharp lines between all three.

---

## The Three Concepts at a Glance

| Term | Source | Timing | Intentional? | Example |
|------|--------|--------|--------------|---------|
| Interrupt | External hardware | Asynchronous | No | NIC packet arrival, timer tick |
| Exception | CPU itself | Synchronous | No | Divide-by-zero, page fault |
| Trap | Software instruction | Synchronous | Yes | `syscall`, `int 0x80`, breakpoint |

---

## Interrupts

An **interrupt** is a signal sent to the CPU by an external device (keyboard, disk controller, network card, timer). The CPU finishes its current instruction, saves its state, and branches to the **Interrupt Service Routine (ISR)** registered for that interrupt number.

Key properties:
- Asynchronous — can arrive at any instruction boundary.
- Usually **maskable**: the CPU can ignore them while executing critical sections.
- After the ISR finishes it executes `iret` (x86) or equivalent to restore saved state.

```asm
; x86 — hardware raises IRQ1 (keyboard)
; CPU pushes EFLAGS, CS, EIP onto the stack
; jumps to handler at IDT[33]
iret   ; handler exit: restores EFLAGS, CS, EIP
```

---

## Exceptions

An **exception** is generated by the CPU itself when an instruction cannot complete normally.

Common x86 exceptions:

| Vector | Name | Type |
|--------|------|------|
| 0 | Divide Error | Fault |
| 13 | General Protection Fault | Fault |
| 14 | Page Fault | Fault |
| 6 | Invalid Opcode | Fault |

Exceptions come in three subtypes:

- **Fault** — recoverable; CPU restores the state to *before* the faulting instruction, so the OS can fix the problem (e.g., load a missing page) and re-execute it.
- **Trap** — execution resumes at the *next* instruction after the trapping instruction (e.g., single-step debug trap).
- **Abort** — unrecoverable hardware error; the process or system is terminated.

---

## Traps (Software Interrupts)

A **trap** is a deliberate exception triggered by a software instruction to request an OS service.

```c
// Linux x86-64 system call — write "hi\n" to stdout
// The 'syscall' instruction raises vector 0x80 (legacy) or
// uses the SYSCALL fast-path, transferring control to the kernel.
mov rax, 1       // sys_write
mov rdi, 1       // fd = stdout
mov rsi, msg     // buffer
mov rdx, 3       // length
syscall          // TRAP into kernel
```

The trap instruction is **synchronous** because it happens exactly where the programmer placed it.  
The CPU switches from user mode to kernel mode, executes the system call handler, then returns.

---

## Why the Distinction Matters

- **Interrupt** — hardware event, async, may be masked.
- **Exception** — CPU fault/trap/abort, sync, caused by the running instruction.
- **Trap** — intentional software-initiated mode switch, sync.

All three use the **same underlying mechanism** on x86 (the IDT + privilege-level switch), but their sources, timing, and intent differ.

---

## Worked Example

A web server is accepting connections. While executing `read()`:

1. The NIC raises IRQ 11 — this is an **interrupt**.
2. The kernel's `read()` system call was entered via `syscall` — this is a **trap**.
3. Inside the kernel, a null pointer dereference occurs — this is an **exception** (General Protection Fault).

> **Interview answer:** An interrupt is an asynchronous signal from hardware; an exception is a synchronous CPU-generated error; a trap is an intentional synchronous instruction that transfers control to the OS. All three share the same dispatch mechanism (the interrupt vector table) but differ in origin and intent.
