# Interrupt Latency and What Affects It

**Interrupt latency** is the time between when a hardware device asserts an interrupt signal and when the first instruction of the ISR begins executing. Minimizing and bounding this latency is critical for real-time systems, audio drivers, high-frequency trading, and any application where missing a deadline causes visible failure.

---

## Defining Latency: Three Sub-Intervals

```
Device asserts IRQ
        │  ← Recognition latency
CPU acknowledges IRQ
        │  ← Dispatch latency
ISR first instruction executes
        │  ← ISR body
Work complete
```

| Phase | Caused By |
|-------|-----------|
| Recognition latency | IF flag, NMI mask, current instruction length |
| Dispatch latency | IDT lookup, stack switch, pipeline flush |
| ISR body | Length of the interrupt handler itself |

The sum of recognition + dispatch latency is what most engineers mean when they say "interrupt latency."

---

## Factor 1 — Interrupts Disabled (IF = 0)

When the CPU executes `cli` (clear interrupt flag) or enters an interrupt gate, **all maskable interrupts are deferred** until `sti` re-enables them. The longer interrupts stay disabled, the higher the worst-case latency.

```asm
cli          ; disable interrupts — any IRQ arriving here is deferred
; ... critical section ...
sti          ; re-enable — deferred IRQs now deliver
```

In Linux, `spin_lock_irqsave()` disables interrupts to protect shared data; long critical sections here are a latency enemy.

---

## Factor 2 — Long-Running Instructions

The CPU finishes the current instruction before checking for interrupts. Most instructions are fast, but some are long:

| Instruction | Approximate Cycles |
|-------------|-------------------|
| `rep movs` (large block copy) | Hundreds to thousands |
| `cpuid` | 20–100 |
| `rdmsr` / `wrmsr` | 30–100 |
| `div` (64-bit) | 30–90 |
| Normal ALU | 1–4 |

On real-time systems, avoid long string instructions in hot paths.

---

## Factor 3 — Cache and TLB State

The IDT, kernel stack, and ISR code may be **cold in cache** when the interrupt fires. A cache miss can add tens to hundreds of nanoseconds. Techniques to mitigate:

- Pin ISR code and data to always-resident ("wired") memory.
- Use `prefetcht0` hints if the ISR is on a known periodic schedule.
- Keep ISRs small so they fit in the L1 instruction cache.

---

## Factor 4 — Interrupt Controller Overhead

The path from device to CPU involves the APIC:

```
NIC → PCIe → IOMMU → APIC → CPU LINT0
```

Each hop adds latency. MSI (Message Signaled Interrupts) short-circuit the APIC by writing directly to a CPU register, reducing this overhead compared to legacy pin-based IRQs.

---

## Factor 5 — SMM (System Management Mode) Interrupts

System Management Interrupts (SMI) are generated by firmware (UEFI/BIOS) and cause the CPU to enter **SMM** — an invisible, non-maskable mode that can pause normal execution for 50–200 µs or more. SMIs are the bane of real-time Linux. Tools like `hwlatdetect` and `rtla` measure SMI jitter.

```bash
# Measure hardware latency (including SMI) on Linux:
hwlatdetect --duration=60s
```

---

## Factor 6 — SMP and IRQ Affinity

On multi-core systems, an IRQ may be routed to a core that is in a long critical section. IRQ affinity (`/proc/irq/N/smp_affinity`) pins IRQs to specific cores to avoid this.

---

## Measuring Interrupt Latency

```bash
# /proc/interrupts shows cumulative counts per CPU
cat /proc/interrupts

# cyclictest measures wakeup latency (user-space proxy for IRQ latency)
cyclictest -m -p 99 -d 0 -n --duration=60
```

A well-tuned PREEMPT_RT kernel achieves worst-case latency below 100 µs on commodity hardware.

---

## Worked Example

A hard real-time audio system must process a 512-sample buffer every 11.6 ms (44.1 kHz, 512 samples). The interrupt latency budget:

| Component | Budget |
|-----------|--------|
| Max disabled-interrupt window | 10 µs |
| ISR dispatch overhead | 1 µs |
| ISR body | 50 µs |
| DMA refill | 200 µs |
| Total | <<11,600 µs |

Any SMI or long `rep movs` that takes the system past ~11.6 ms causes an audio dropout (xrun).

> **Interview answer:** Interrupt latency is the time from device assertion to the first ISR instruction. It is increased by: disabled interrupts (IF=0), long-running CPU instructions, cold caches, APIC routing overhead, SMM firmware interruptions, and poor IRQ affinity. Real-time systems minimize it by using PREEMPT_RT kernels, short critical sections, and IRQ isolation.
