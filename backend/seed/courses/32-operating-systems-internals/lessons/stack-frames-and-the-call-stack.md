# Stack Frames and the Call Stack

Every function call creates a **stack frame** (also called an **activation record**) — a structured region of stack memory that holds everything the function needs to execute. Understanding stack frames explains how recursion works, how debuggers show backtraces, and why certain bugs cause mysterious crashes.

## What Lives in a Stack Frame

A typical x86-64 stack frame contains:

- **Return address** — where execution resumes after the function returns.
- **Saved frame pointer (RBP)** — pointer to the caller's frame, so the debugger can walk up the call stack.
- **Local variables** — stack-allocated variables declared inside the function.
- **Saved registers** — caller-saved or callee-saved registers the function needs to preserve.
- **Arguments** — for functions with more arguments than fit in registers (on x86-64, the first 6 integer args go in registers).

```
High address
+---------------------------+  <- caller's stack frame
|  ... caller locals ...    |
+---------------------------+
|  argument 7+ (if any)     |  <- pushed by caller
+---------------------------+
|  return address           |  <- pushed by CALL instruction
+---------------------------+
|  saved RBP                |  <- pushed by callee prologue
+---------------------------+  <- RBP points here (frame base)
|  local variables          |
|  saved registers          |
+---------------------------+  <- RSP (stack pointer, grows down)
Low address
```

## The Function Prologue and Epilogue

Every function generated by a compiler starts with a **prologue** and ends with an **epilogue**:

```asm
; Prologue
push rbp          ; save caller's frame pointer
mov  rbp, rsp     ; set our frame pointer
sub  rsp, 32      ; allocate space for locals

; ... function body ...

; Epilogue
mov  rsp, rbp     ; restore stack pointer
pop  rbp          ; restore caller's frame pointer
ret               ; pop return address and jump to it
```

The `ret` instruction pops the return address from the stack and jumps to it, returning control to the caller.

## Tracing the Call Stack

Consider this C code:

```c
int add(int a, int b) {
    return a + b;
}

int compute(int x) {
    int result = add(x, 10);
    return result;
}

int main(void) {
    int val = compute(5);
    return 0;
}
```

When `add` is executing, the call stack (from bottom to top) is:

```
main       <- bottom (first frame)
  compute  <- middle frame
    add    <- top frame (currently executing)
```

Each frame has its own copy of local variables. `result` in `compute` and `val` in `main` are completely independent stack slots.

## Stack Frame and Variable Scope

Local variables are **not initialized automatically** in C — they contain whatever garbage was on the stack previously. This is a critical distinction from heap memory (which `calloc` can zero-initialize):

```c
void demo(void) {
    int x;           // uninitialized — reads from it are UB in C
    int y = 0;       // explicitly zeroed
    printf("%d\n", x);  // undefined behavior!
}
```

## Why Debuggers Show Backtraces

A debugger can reconstruct the call chain by **walking the frame pointer chain**. Starting from `RBP`, it reads the saved `RBP` at `[RBP]` to find the caller's frame, and reads the return address at `[RBP+8]`. It repeats this up through the chain until it reaches the bottom of the stack.

Modern compilers often omit the frame pointer (`-fomit-frame-pointer`) for performance, relying on `.eh_frame` or DWARF unwind tables instead — which is why some crash dumps show incomplete backtraces on optimized binaries.

## Common Pitfall: Stack Buffer Overflows

Writing past the end of a stack-allocated array can overwrite the saved return address, enabling an attacker to redirect execution:

```c
void vulnerable(const char *input) {
    char buf[64];
    strcpy(buf, input);  // no bounds check — classic stack smashing!
}
```

Modern mitigations include **stack canaries** (a secret value placed before the return address), **ASLR** (randomizing stack address), and **NX bits** (making the stack non-executable).

## Interview Answer

> "A stack frame holds the return address, saved registers, and local variables for one function call. The CPU's stack pointer tracks the top; the frame pointer tracks the base. When a function returns, its frame is destroyed by restoring RSP, giving instant O(1) deallocation."
