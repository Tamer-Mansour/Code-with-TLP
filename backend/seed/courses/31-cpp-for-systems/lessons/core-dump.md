# Core Dumps: Capturing and Analyzing Crashes

A core dump is a snapshot of a process's memory, registers, and call stack at the exact moment it crashed. Unlike a log message or a stack trace printed to stderr, a core dump preserves everything — you can load it into gdb hours or days later and inspect the full program state as if you were there when it died.

## Enabling Core Dumps

By default, most Linux systems suppress core dumps. The `ulimit` command controls this per-shell session:

```bash
ulimit -c unlimited     # allow core dumps of any size
ulimit -c               # check current limit (0 = disabled)
```

To make this permanent, add it to `/etc/security/limits.conf`:

```
*    soft    core    unlimited
*    hard    core    unlimited
```

## Where Core Files Are Written

The kernel writes core files according to the pattern in `/proc/sys/kernel/core_pattern`:

```bash
cat /proc/sys/kernel/core_pattern
# Default: "core" — writes a file named "core" in the CWD
# Or: "|/usr/lib/systemd/systemd-coredump %P %u %g %s %t %c %h"
# (systemd coredumpd captures it instead)
```

Set a useful pattern including PID and timestamp:

```bash
echo "/tmp/cores/core.%e.%p.%t" | sudo tee /proc/sys/kernel/core_pattern
```

| Pattern token | Meaning |
|---------------|---------|
| `%e` | Executable name |
| `%p` | PID |
| `%t` | Time (Unix timestamp) |
| `%s` | Signal number that caused the crash |
| `%u` | User ID |

## Generating a Core Dump

Any unhandled fatal signal — `SIGSEGV`, `SIGABRT`, `SIGBUS`, `SIGFPE` — produces a core dump if they are enabled.

You can also force one from within the program:

```cpp
#include <csignal>

// Cleanly trigger a core dump from code
raise(SIGSEGV);   // not ideal — use abort() instead
abort();          // sends SIGABRT, always dumps core
```

Or send a signal from another terminal:

```bash
kill -SIGSEGV <pid>
kill -SIGABRT <pid>
```

## Analyzing a Core Dump with gdb

You must provide the original binary (with debug symbols) alongside the core file:

```bash
gdb ./myapp core.myapp.1234.1700000000
```

gdb loads the core and immediately shows the crash state:

```
Core was generated by `./myapp --config /etc/myapp.conf'.
Program terminated with signal 11, Segmentation fault.

#0  process_packet (pkt=0x0, len=256) at network.cpp:134
(gdb)
```

From here, all normal gdb commands work exactly as in a live session:

```
(gdb) bt full               # full backtrace with local variables
(gdb) frame 0
(gdb) print pkt
$1 = (Packet *) 0x0         # null pointer — root cause identified
(gdb) print len
$2 = 256
(gdb) info registers
```

## Worked Example: Diagnosing a Field Crash

A server crashes in production overnight. The ops team collects the core file. You have the matching binary built with `RelWithDebInfo`:

```bash
gdb ./server_v2.3 /var/crash/core.server.4421.1700005200
```

```
(gdb) bt
#0  0x00007f2c3a1b4d12 in __memcpy_avx_unaligned ()
#1  0x000000000041f230 in Session::forward_data (this=0x7f2c280b4010,
    buf=0x7f2c280c0000 "...", sz=65536) at session.cpp:287
#2  0x0000000000420a10 in EventLoop::dispatch (this=0x6050c0)
    at eventloop.cpp:412

(gdb) frame 1
(gdb) info locals
buf    = 0x7f2c280c0000
sz     = 65536
dst_   = 0x7f2c280bffe0   # 32 bytes before end of a 65536-byte region!
```

The destination pointer `dst_` is near the very end of the buffer. Copying 65536 bytes from that position would overflow. A size calculation bug is the culprit.

## systemd-coredump

On systems using systemd, crashes are captured automatically by `systemd-coredump`:

```bash
coredumpctl list               # list all captured core dumps
coredumpctl info               # details about the most recent crash
coredumpctl gdb                # open the most recent core in gdb
coredumpctl gdb -1             # same (most recent)
coredumpctl gdb PID            # specific crash by PID
```

`coredumpctl` handles storage, compression, and retrieval transparently.

## Common Pitfall: Binary Mismatch

If the binary has been rebuilt since the crash, the core dump is useless — addresses no longer correspond to the same functions. Always archive versioned binaries (or their debug symbol files) alongside any deployed release.

```bash
# Save the binary hash at deploy time
sha256sum ./myapp > myapp.sha256

# Before analyzing a core, verify the binary matches
sha256sum -c myapp.sha256
```

> **Interview answer:** Enable core dumps with `ulimit -c unlimited`, then run `gdb ./binary core` to load the snapshot. gdb recreates the full program state at crash time — you get the backtrace, local variables, and memory contents exactly as they were, even long after the process is gone.
